# Memory optimization audit

Date: 2026-11-15. Scope: current working tree, including the restored modal animation. GPT-6.1 Sol XHigh provided an independent review. This audit proposes changes; it does not implement the memory optimizations or claim measured savings.

## Findings, in recommended order

1. **Avoid copying Urban results on each render.** `src/ui.rs:1660` builds a temporary owned `Entry`, cloning definitions and examples before the shared renderer copies display text again. Add a borrowed Urban adapter to the existing `EntryContentSource` interface. Preserve the order and grouping of parts of speech, credits, full text, selectable text, and updates. The benefit grows with result length and repaint frequency; the allocation reduction is not yet measured.

2. **Avoid full text in selection element IDs.** `src/ui.rs:2013` and nearby example and credit IDs embed entire strings in addition to the displayed text. Use compact structural IDs with a content generation/version that changes when the underlying text changes. Preserve selection for unchanged content and invalidate it for replaced content, including same-word refreshes; do not rely on a collision-prone hash alone. Compare allocation counts and test dragging, selection across repaints, result replacement, and duplicate definitions.

3. **Stop obsolete work without removing search functionality.** `src/ui.rs:422` and `:451` detach a lookup and Urban job per submission; sequence checks suppress old results but do not stop their work. Coalesce duplicate in-flight searches and cancel or bound superseded jobs, including their curl and optional classifier children. Ensure the latest query is not starved, each enabled source still completes, and children are reaped on all exits. This reduces peak memory under rapid searches; it is not evidence of a leak or a quantified idle-memory saving.

4. **Reduce simultaneous response representations.** `src/model.rs:258` reads each complete curl response into a `String`; `src/urban.rs:265` and `:319` then deserialize the entire list before retaining the existing selected entries. Explore incremental JSON parsing and skipping unneeded records while still validating the complete response. For paths requiring full HTML or text, investigate streaming or temporary-file spooling with bounded in-memory buffering. Preserve full accepted results, current error behavior, and source order. A hard response-size cutoff could reject currently accepted results, so do not introduce one as a feature-preserving optimization without an explicit product decision. Reap subprocesses on read, parse, cancellation, and error paths; the current read-error path can bypass `wait()`.

5. **Remove short-lived daily cache clones.** `src/ui.rs:272` clones the two loaded word lists while retaining the cache wrappers briefly; move their words and timestamps into the view instead. `src/daily_cache.rs:108` clones words before serializing; use a borrowed serialization structure. Keep the cache format, validation, timestamps, atomic replacement, and failure behavior. Likely modest savings because each cache holds two entries.

6. **Reduce suggestion and recommendation allocation churn after profiling.** `src/model.rs:607` allocates candidate character vectors and collects every qualifying suggestion before sorting, although only three are returned. Reuse scratch space and retain the best three using the same score and lexical tie order. `src/model.rs:210` and `src/similar.rs:180` stream Webster records but construct temporary entries and tokens per candidate; investigate a borrowed or specialized scoring path while preserving ranking, duplicate handling, randomness, cancellation, and the full corpus. These are primarily transient-allocation candidates, not proven major retained-memory savings.

## Existing safeguards and exclusions

- Webster lookups stream a compressed bucket and skip other records instead of retaining a full decoded dictionary. Similar-word ranking is already bounded and cooperatively cancellable; daily cache reads are bounded. Do not replace these with an unbounded decoded dictionary cache without measuring its memory cost.
- The current modal draws one page and a dimming layer (`src/ui.rs:1348`, `:2041`) and retains the open/close animation. The 38-page blur finding in the older `AUDIT.md` no longer describes the current implementation. Do not remove or degrade the animation to obtain memory savings.
- Avoid truncating definitions, reducing displayed results, disabling optional classification, removing the daily cache, or weakening selection to save memory. Bound concurrency and temporary buffers while retaining behavior.

## Measurement and validation plan

Use an isolated Xvfb instance, software renderer, private session bus, private XDG directories, and deterministic mock sources. Record application RSS and PSS (and subprocess memory separately) at idle, after offline and online results, with a long result, during rapid replacement searches, and across repeated modal open/close cycles. Capture allocation counts and peak live heap with a suitable profiler; RSS alone includes shared mappings, renderer allocations, and allocator retention, and cannot establish a leak. Compare identical release builds, fixtures, timings, and renderer settings before and after each change. Observe whether memory stabilizes over repeated cycles and report the measurements and limitations; no application heap or RSS baseline was collected for this audit.

Run the existing offline suite and add focused tests for result equivalence, changed-content selection invalidation, slow/cancelled fake children, process reaping, and full-response handling. Check opening and closing animations and long-result selection in the isolated GUI, including reduced motion, before considering any rendering optimization complete. The older `AUDIT.md` contains historical CPU and safety findings and is not a current memory profile.
